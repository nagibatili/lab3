# Отчёт о проделанной работе

**Проект:** FoodCampus (сквозной практический кейс)
**Практическая работа:** «Реализация программных модулей по Пользовательским историям (User Stories) и Архитектуре»

## 1. Цель работы

Научиться реализовывать программный модуль на основе User Story и утверждённого архитектором интерфейса, разработать тестовый драйвер, провести негативное тестирование, найти и зафиксировать реальные дефекты, а также подготовить отчёт о проделанной работе.

## 2. Выбранный модуль и User Story

| Параметр | Значение |
|---|---|
| Модуль | **MenuModule** |
| User Story | «Как повар, я хочу фильтровать блюда по категориям, чтобы выдавать актуальное меню» |
| Зона ответственности | Хранение списка блюд, фильтрация по типу (суп, второе) и наличию |
| Интерфейс (метод) | `get_filtered_menu(category, only_available)` |

Модуль выбран как один из четырёх, предложенных в задании; дополнительных требований «использовать другой модуль» в задании нет.

## 3. Описание реализации

Файл `menu.py`, класс `MenuModule`. Код написан на Python 3, без сторонних библиотек.

**Данные.** Блюдо — это словарь с обязательными полями:

- `name` — название (непустая строка);
- `category` — категория блюда («суп», «второе», ...);
- `price` — цена, число 0 или больше;
- `available` — наличие, `True`/`False`.

Список блюд хранится внутри объекта (`self.dishes`), исходный список задаётся через `MenuModule(dishes)` или пополняется методом `add_dish`.

**Методы:**

- `add_dish(dish)` — проверяет блюдо (обязательные поля, типы, непустые строки, цена не отрицательная, `available` — булево) и добавляет его; при ошибке выбрасывает `ValueError` с понятным сообщением;
- `get_filtered_menu(category, only_available=False)` — интерфейсный метод: фильтрует по категории и/или наличию, возвращает новый список с копиями блюд; проверяет аргументы, при ошибке — понятный `ValueError`;
- `get_all_dishes()` — копия полного списка блюд;
- `get_categories()` — список категорий, которые есть в меню.

**Ключевые решения:**

- категория нормализуется (`strip().lower()`): «Суп», «СУП», «  суп  » и «суп» — одна категория;
- методы возвращают **копии** блюд, чтобы вызывающий код случайно не испортил внутренний список;
- пустое меню обрабатывается так же, как обычное: возвращается пустой список;
- молчание недопустимо: на некорректные данные всегда есть понятная ошибка, но неизвестная корректная категория («напиток») — это нормальный пустой результат, а не ошибка.

**Шаг 4 задания (зависимости и Stub):** MenuModule не зависит от других модулей системы (Корзины, Скидок, Чека), поэтому заглушка (Stub) не потребовалась.

## 4. Тестовые драйверы

1. **`test_menu.py`** — автоматические тесты на стандартном `unittest`. Покрытие: фильтрация по категории; по наличию; оба фильтра одновременно; пустое меню; отсутствие результатов (неизвестная категория); некорректные данные (число/None/пустая строка вместо категории, не-словарь вместо блюда, отсутствующие поля, отрицательная цена, цена строкой, `available` строкой и т.д.); граничные случаи (цена 0, нормализация категории, копии результата, конструктор с готовым списком).
   Команда: `python -m unittest test_menu.py -v`.
2. **`test_runner.py`** — драйвер-сценарий в стиле примера из задания (печать результата + `assert` для позитивных сценариев, `try/except` для негативных). Использовался как основной инструмент негативного «стресс-тестирования» первой версии модуля.
   Команда: `python -X utf8 test_runner.py`.

## 5. Порядок работы и найденные дефекты

Работа велась в два шага, как требует задание: сначала — первая рабочая версия, затем её негативное тестирование и исправление.

**Шаг 1 — версия 1.** Написана первая рабочая версия модуля (хранение + фильтрация без проверки данных). Позитивные сценарии прошли, негативное тестирование выявило **4 дефекта** (все воспроизведены реально, вывод консоли зафиксирован):

| ID | Дефект (кратко) | Критичность |
|---|---|---|
| BUG-01 | Блюдо без поля `category` принято молча, затем `get_filtered_menu` упал с `KeyError: 'category'` — любое обращение к меню стало приводить к падению программы | высокая |
| BUG-02 | Число, `None` или пустая строка вместо категории — молча возвращается `[]`, ошибка пользователя скрыта | средняя |
| BUG-03 | «Суп»/«СУП»/«  суп  » не находят супы из-за чувствительности к регистру и пробелам — блюда «исчезают» из меню | средняя |
| BUG-04 | `add_dish` принял блюдо с отрицательной ценой `price: -50` | средняя |

Инструменты негативного тестирования по шагам задания: «стресс-тест» заведомо неверными данными (текст вместо числа, число вместо текста, слишком длинные/пустые строки — покрыты тестами `TestInvalidArguments`).

**Шаг 2 — версия 2 (исправление).** В код добавлены: проверка обязательных полей и типов при `add_dish`, проверка аргументов в `get_filtered_menu`, нормализация категории, защита внутреннего списка копиями. После исправлений повторно запущены оба драйвера.

Подробности каждого дефекта (входные данные, ожидаемое/фактическое поведение, шаги воспроизведения, фактический вывод) — в файле `bug_report.md`.

## 6. Результаты тестирования (фактические)

На исправленной (итоговой) версии:

- `python -m unittest test_menu.py -v` → **`Ran 42 tests in 0.002s` — OK**, код возврата 0. Среди них 21 тест — проверки на некорректные данные (закрепляют исправления BUG-01…BUG-04);
- `python -X utf8 test_runner.py` → позитивные сценарии пройдены; поиск «Суп»/«СУП»/«  суп  » находит 2 супа; 12 негативных сценариев завершаются понятным `ValueError` (все `[OK]`); блюдо без поля отклоняется при добавлении, `get_filtered_menu` не падает; цена 0 принимается; код возврата 0;
- `python test_runner.py` без флага работает, но в консоли Windows русский текст искажается кодировкой — в README указана команда с `-X utf8`.

До исправлений из этих тестов выполнялись бы только «позитивные»: например, тест `test_add_negative_price` проявил бы дефект версии 1 — молчаливое принятие отрицательной цены; это поведение зафиксировано в bug_report.md с фактическим выводом консоли.

## 7. Вывод

Реализован модуль MenuModule по User Story и утверждённому интерфейсу: хранение блюд, фильтрация по категории, по наличию и совместная фильтрация. Разработаны два тестовых драйвера. Негативное тестирование первой версии позволило обнаружить 4 реальных дефекта, включая критическое падение `KeyError`; все они задокументированы в Bug Report и исправлены. Повторное тестирование итоговой версии прошло успешно. Практика показала: без проверки входных данных «сломанное» блюдо может вывести из строя весь модуль, а молчаливое возвращение пустого результата прячет ошибки от пользователя — такие ситуации нужно делать видимыми.
